HOMEWORK 1 · EXERCISE 2

From mnemonic to checksummed Ethereum address

A conventional BIP-39/BIP-32 Ethereum wallet combines several primitives because generating secrets, deriving related accounts, signing messages, hashing data and detecting transcription mistakes are different problems. The pipeline below concerns an externally owned account (EOA), not a contract address.

01 · BIP-39Mnemonic → seed

Encode entropy as words; derive a 64-byte seed with PBKDF2-HMAC-SHA512.

02 · BIP-32 / BIP-44Seed → private key

Derive an HD tree and select a leaf using a standard path.

03 · secp256k1Private → public key

Compute Q = kG. The private key can later create digital signatures.

04 · SerializationPublic point → bytes

Use x || y, each coordinate 32 bytes. Omit the uncompressed 0x04 prefix.

05 · Keccak-256Public bytes → address

Hash 64 bytes and retain the final 20 bytes: a 160-bit address.

06 · EIP-55Address → mixed case

Encode error-detection information in the case of hexadecimal letters.

1. Role of each standard and primitive

TechnologyRole and purpose
BIP-39 [1]Generate 128–256 random entropy bits in multiples of 32, append the first ENT / 32 bits of SHA-256(entropy), and split into 11-bit indices in a 2,048-word list. This yields 12, 15, 18, 21 or 24 words. Normalize mnemonic and optional passphrase with UTF-8 NFKD. PBKDF2-HMAC-SHA512, 2,048 iterations, uses the mnemonic as password and "mnemonic" + passphrase as salt to derive a 64-byte seed.
BIP-32 [2]Derive a tree of extended keys from the seed using HMAC-SHA512. An extended private node contains a private scalar plus a 32-byte chain code. Both hardened and normal child derivations are supported; an extended public key can derive only normal public children.
BIP-44 [3]Assign meanings to levels in a BIP-32 tree: m / purpose' / coin_type' / account' / change / address_index. An example Ethereum path is m/44'/60'/0'/0/0: purpose 44, registered coin type 60, first account, external branch, first address. An apostrophe means hardened derivation. BIP-44 is a path convention, not a hash or a new source of randomness. [4]
secp256k1 [5]Define the elliptic-curve group and the relationship Q = kG. Ethereum EOA signatures use ECDSA over this curve: a private key signs and the public key verifies. Scalar multiplication derives the public key; it does not encrypt the private key, and a hash alone cannot replace a signature.
Keccak-256 [6]Hash the 64-byte uncompressed coordinate sequence x || y, without the SEC1 prefix 04. Retain the rightmost 20 digest bytes, then display them as 40 hex characters with the 0x prefix. This address is an identifier derived from the public key, not the public key itself.
EIP-55 [7]Hash the lowercase 40-character hex address as ASCII, without 0x, using Keccak-256. At each letter position, uppercase it if the corresponding digest hex digit is at least 8; otherwise use lowercase. Digits stay unchanged. The 20 address bytes do not change; capitalization carries checksum information.

A BIP-39 passphrase is not the wallet application's local unlock password. Every passphrase produces a seed; a typo usually opens a different wallet rather than reporting an incorrect passphrase. Reproducing a wallet therefore requires the mnemonic, its exact optional passphrase, and the intended derivation path. BIP-39 is a common wallet convention, not an Ethereum consensus requirement; different wallets can support different recovery and path conventions. [1]

2. BIP-32 derivation in more detail

The master HMAC output is split into a scalar and chain code. Each child combines its parent's chain code, a serialized key and a child index. The word “Bitcoin” below is a literal BIP-32 domain string; its use also applies when the derived leaf is used for Ethereum.

I = HMAC-SHA512(key = ASCII("Bitcoin seed"), data = seed) I = I_L || I_R (32 bytes each) k_master = parse256(I_L); c_master = I_R Normal child i < 2³¹: data = serP(Q_parent, compressed) || ser32(i) Hardened child i ≥ 2³¹: data = 0x00 || ser256(k_parent) || ser32(i) I = HMAC-SHA512(key = c_parent, data = data) k_child = (parse256(I_L) + k_parent) mod n c_child = I_R

All integers are serialized in big-endian form. For the master, I_L = 0 or I_L ≥ n is invalid. For a child, I_L ≥ n or a zero resulting scalar is invalid and BIP-32 proceeds to the next index. The demo explicitly reports such a case instead of silently changing the displayed path. Hardened derivation uses i = index + 2³¹ and requires private information. The public keys used internally for normal BIP-32 derivation are compressed; the 64-byte Ethereum address hash input is not. [2]

What changes? Keeping the mnemonic and passphrase fixed reproduces the same seed and keys. Increasing the final path index selects a different normal child without changing the seed. Switching to TREZOR changes the seed itself and therefore the entire HD tree. Changing only EIP-55 capitalization leaves the underlying 20-byte address unchanged.

The local experiment makes no blockchain calls and does not simulate opening MetaMask, Rabby or another application. Creating an address is an offline computation; signing and broadcasting a transaction are separate operations. The JavaScript implements the secp256k1 and Keccak steps and uses native Web Crypto for SHA-2, HMAC and PBKDF2. It creates no signatures and stores no secrets.

Experiment A gives 256 distinct addresses. The 10,240 hex digits have a Pearson chi-square statistic χ² = 19.10625 against equal expected frequencies of 640 (15 degrees of freedom). This is a descriptive comparison with a simple uniform model; it is not a certification of uniformity or cryptographic security. Pearson correlation between the index and the leading 32-bit key word is 0.109930; for the leading 32-bit address word it is −0.001308. These specific, limited projections do not test all dependencies. Adjacent address indices differ in an average of 79.6196 / 160 address bits, near the idealized independent-bit expectation of 80. Adjacent indices may differ in several input bits, so that last measurement is not a strict avalanche test.

Experiment B — controlled Keccak diffusion. For each four-byte, big-endian message ser32(i), with i = 0, …, 255, toggle each of its 32 input bits separately and compare the 256-bit digests. The 8,192 directed one-bit trials give a mean Hamming distance of 127.9296 / 256 bits (49.9725%), with range 100–157. The idealized fair-bit expectation is 128. Some message pairs are visited in both directions; the observations are not all independent. The sample shows diffusion consistent with avalanche-like behavior but cannot establish the strict avalanche criterion or any resistance to preimages or collisions.

Interpretation by stage

Mnemonic and seed. A valid 12-word BIP-39 phrase encodes 128 entropy bits plus four checksum bits, not 132 independently random bits. Only one sixteenth of arbitrary 12-word strings passes that checksum under the uniform-bit model. PBKDF2's 512-bit seed length does not turn 128 bits of entropy into 512 bits of security; a strong optional passphrase may add secret entropy, while a predictable one adds little. The repeated public mnemonic in this experiment has no secrecy.

HD keys and public points. HMAC-based child material should look pseudorandom to an observer lacking the required secret information, but the derivation is deterministic and its nodes are not new independent random draws. The valid scalar range and curve equation constrain the outputs. A 512-bit point serialization does not contain 512 independent random bits; the point contains approximately 256 bits of information. Balanced bit counts are useful diagnostics, not security proofs.

Hashes and addresses. Well-designed hashes aim for preimage, second-preimage and collision resistance; balanced output bits and diffusion are observable supporting behaviors. Taking 20 bytes restricts addresses to a 160-bit space. In an idealized model, generic target-preimage search scales as 2¹⁶⁰ trials and generic birthday collisions as 2⁸⁰, independently of the approximately 128-bit generic ECDLP security for a known secp256k1 public key. Finding some address collision is not automatically a way to take control of a particular existing account. No repeated address among 256 samples is unsurprising and cannot establish collision resistance.

Checksum encoding. EIP-55 intentionally correlates letter case with a hash of the address. Case bits are neither extra address entropy nor proof of identity. The specification reports an average of 15 check bits and approximately 0.0247% accidental acceptance for its random mistype model; this is not a universal probability for every error pattern or an adversarial guarantee. [7]

6. SHA-2 / SHA-512 versus Keccak / SHA-3

AspectSHA-2 / SHA-512Keccak / SHA-3
Design familySHA-2 uses an iterative compression-function structure. SHA-512 produces a 512-bit digest.Keccak uses a sponge construction built from a permutation. NIST selected Keccak as the basis of SHA-3.
Role hereSHA-256 supplies BIP-39 checksum bits; HMAC-SHA512 supports PBKDF2 and BIP-32.Ethereum uses Keccak-256 for EOA address derivation and EIP-55.
CompatibilitySHA-512 is not Keccak and cannot replace it while preserving outputs.Ethereum's Keccak-256 is not standardized SHA3-256: their padding/domain-separation conventions differ.
Input: empty byte string Keccak-256 = c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470 SHA3-256 = a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a

Both 256-bit functions use the Keccak-f[1600] permutation with rate 1,088 bits and capacity 512 bits, but legacy Keccak-256 uses the byte-level delimited suffix 0x01, whereas SHA3-256 uses 0x06, followed by the final padding bit. Consequently, a function named sha3_256 is not a drop-in Ethereum Keccak implementation. The distinct empty-input outputs above are also checked by the program. [10] [12]

8. Why not use a single algorithm for everything?

BIP-39 makes a backup human-readable and derives seed material; BIP-32 builds a reproducible account tree; BIP-44 tells compatible software where to look. secp256k1 supplies an asymmetric relationship so a secret key can sign while its public counterpart verifies. Keccak-256 produces fixed-size digests and compact address identifiers. EIP-55 adds transcription-error detection to a human-facing representation.

These guarantees are not interchangeable. A hash of a secret does not, by itself, create a digital-signature scheme. An elliptic-curve public point is not a mnemonic backup or a general-purpose digest. A checksum can be recomputed by anyone and does not establish ownership. Encoding changes representation, not the underlying secret's unpredictability. The pipeline works by composing primitives with different, explicit roles and by using the required byte formats at each boundary.
